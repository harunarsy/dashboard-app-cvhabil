## Non-Negotiable Rules

1. Database PostgreSQL is strictly read-only throughout this roadmap. No `INSERT`, `UPDATE`, `DELETE`, DDL, migration, or mutating script may be executed.
2. Database test sessions must fail closed in read-only mode and prove `transaction_read_only = on` before data-dependent tests run.
3. Every reported result must come from actual command output.
4. Existing Node/npm paths remain available until replacement parity is proven.
5. Each phase or independently reversible frontend subphase is committed separately and follows repository-wide version synchronization rules.
6. Existing user changes in the original worktree must not be modified or imported implicitly.
7. The Smart-Assistant must be transparent about being rule-based. It must never imply that deterministic output is generated by an LLM.

## Autonomous Advance and Hard Stops

Advance automatically only when the phase pass criteria are satisfied. Retry a recoverable technical failure at most three times with a different evidence-based correction.

Hard stop when any of the following occurs:

- Database read-only mode cannot be proven before a DB-connected command.
- A database write is attempted or observed.
- A new test regression appears beyond the recorded baseline and remains after three corrective attempts.
- Dependency resolution changes materially without a safe explanation or rollback.
- A security, authentication, authorization, or data-exposure regression is detected.
- A destructive removal may affect a consumer that cannot be verified from the repository.
- A required business artifact or contract is missing and cannot be safely inferred.
- The worktree contains unrelated user changes that overlap the active phase.

## Phase 6 — Habil Smart-Assistant

### Product Contract

- Name: **Habil Smart-Assistant**.
- Transparent supporting copy: **Rule-based smart suggestions** or equivalent plain-language explanation.
- The experience may feel intelligent and premium, but must not claim or imply generative LLM capabilities.
- Recommendations should expose their reason/evidence where practical.

### Rule Engine

1. Search and extract existing deterministic insight, recommendation, anomaly, stock, purchase-order, pricing, and business-rule logic.
2. Prefer consolidating existing Node.js logic. Do not add Python unless a real requirement appears.
3. If no suitable engine exists, implement a Node.js rule engine using existing read-only business data and documented thresholds.
4. Add `backend/routes/ai.js` as a stable JSON interface with authentication, authorization, rate limiting, request timeout, output-size bounds, structured errors, and strict read-only DB behavior.
5. Keep engine logic separate from transport so it can be tested without HTTP or database writes.

### UI

1. Build a trustworthy assistant surface with clear processing, empty, success, and error states.
2. Support accessible keyboard/focus behavior, reduced motion, mobile layouts, and readable structured recommendations.
3. Use glass/translucent styling only as a restrained visual accent with sufficient contrast.
4. Do not use copy, animation, or simulated behavior that suggests an LLM is generating text.
5. Run Impeccable validation in bounded desktop/mobile passes.

Run unit, route, HTTP, frontend, build, accessibility, and read-only DB checks. Synchronize version, commit, and complete.

## Phase 7D — Explicit Schema Lifecycle

1. Remove all route-level `ensureSchema`, `ensureTable`, import-time DDL, seed, sequence repair, and backfill execution.
2. Preserve that logic in an ordered migration registry under `backend/migrations/`.
3. Expose a deployment-only runner guarded by an explicit enable flag, exact-host confirmation, environment target checks, lock/statement timeouts, and rollback on failure.
4. Keep normal Node/Bun startup DDL-free and make missing schema fail at the requesting route instead of silently mutating the database.
5. Prove the boundary through static inventory, mocked development import, HTTP smoke, and runner refusal tests.
